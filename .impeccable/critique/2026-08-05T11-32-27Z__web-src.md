## Design Specificity Verdict

**The design system is unmistakably this product. The pages built on it mostly aren't — and the one mechanism the product exists for has almost no interface.**

## Overall Impression

You have built a genuinely good design system and then under-invested in the twenty seconds the entire product exists for.

The foundations are real — one token file, a single owned status map, a pure unit-tested nav-permission function, primitives extended rather than re-rolled. The epistemic honesty is better than most production systems: `executiveInsights.ts` is documented as rule-based not AI, forecasts carry per-card assumption lines, the audit page states that recorded values never leave the server. That is Principle 5 implemented rather than asserted.

But the officer deciding "is this the same person?" — audited under their name, determining whether a citizen is double-registered or wrongly denied — sees the *existing* record's five fields, a bare `score 0.87`, three chips, and two empty panels reading "populates in Phase 4". **The incoming row is never shown.** A comparison interface that renders one side of the comparison is not a comparison interface. And on save: no toast, no transition, nothing.

**The single biggest opportunity:** the peak of this product is currently its flattest moment. Fix the adjudication screen and you fix the specificity verdict, the cognitive-load failures, and heuristics 1, 7 and 8 simultaneously.

## What's Working

**1. The activity → upload → adjudicate → commit → activity-detail loop is a real, closed, product-specific flow.** `ActivityFormModal` branches correctly on `involves_beneficiaries` (No → single step, target field not rendered at all; Yes → mandatory upload step with no skip affordance). `ImportBatchPage` detects the wizard batch via `activity_id === null && draft_activity_name !== null` and relabels its own header and commit button. It works because every step knows what the previous step was for, and it lands the officer on the artifact they set out to build — not a table.

**2. Epistemic honesty is implemented, not disclaimed.** `executiveInsights.ts` is pure rule-based functions over aggregates with stable ordering and per-rule input guards. `forecast.ts` puts a `PROJECTION_LABEL` on every card plus a dashed-rule assumption line. `AdminRegistryPage` states "Completeness measures field PRESENCE, never values". These work because they are specific claims about *mechanism*, not generic disclaimers.

**3. The nav model is disciplined.** `navSectionsFor` (`app/nav.ts:117-130`) is a pure, unit-tested function gating sections by role and items by permission, and `SectionHub` deliberately keeps each area to one rail link instead of exploding sub-tasks into the sidebar. Visibility logic is one testable function, not scattered conditionals.

## Priority Issues

### [P0] The adjudication moment shows only one side of the comparison

**What:** `ImportBatchPage.tsx:136-189` + `MatchRevealPanel.tsx`. The officer sees the existing record's five fields, `score 0.87`, and `matched_fields` as chips. The incoming spreadsheet row's values are never rendered. Half the panel is "populates in Phase 4".

**Why it matters:** PRODUCT.md names this the core value moment. It is audited under the officer's name and decides whether a citizen is double-registered or wrongly denied. The only way to do the job properly is to open the source spreadsheet in another window — which defeats the entire preview-before-save architecture.

**Fix:** Two-column field-level comparison inside `.reviewPanel`: incoming | existing, one row per participating match field, agreements in `--success-ink`, disagreements in `--danger-ink`. Render the score as a position on a band showing `review_threshold` and `auto_accept_threshold` from `MatchingConfig`, so "0.87" reads as "above the 0.72 review threshold, below auto-accept". Delete the Phase 4 placeholders — an empty promise is worse than nothing here. Add a success toast to `useResolveRow`.

**Suggested command:** `/impeccable shape web/src/features/registry` (this is a re-conception, not a polish)

### [P0] The batch workflow cannot handle batches

**What:** `DataTable.tsx:86` renders the select header as an empty `<th aria-label="Select" />` — no select-all. No column anywhere sets `sortable`. `ImportBatchPage` passes the entire `rows` array with no pagination and no filter. `runBulk` (lines 83-91) awaits N sequential `mutateAsync` calls, each invalidating `['import', batchId]` → N full refetches, with no try/catch. And `AdminAuditPage.tsx:167-173` omits the `pagination` prop entirely despite `AuditFilters.page` existing and the API returning `Paginated<AuditEntry>` — **page 1 is the only reachable page of the immutable audit log.**

**Why it matters:** Principle 4 is "the default unit of work is many rows, not one." An officer with 1,800 rows and 150 flagged scrolls an 1,800-row DOM hunting warning badges by eye, clicks 150 checkboxes, then triggers 150 sequential round-trips with no progress and no failure reporting. The product's stated primary workflow is the one it supports worst.

**Fix:** Header select-all with indeterminate state. A segmented filter above the import table — All / Needs review / Errors / Resolved — defaulting to **Needs review**. Paginate or virtualise. Replace the sequential loop with one batch endpoint, or at minimum try/catch it, defer invalidation to loop end, and show "43 of 150". Add the missing `pagination` prop to the audit table.

**Suggested command:** `/impeccable harden web/src/components/DataTable` then `/impeccable layout web/src/features/registry/ImportBatchPage.tsx`

### [P0] The owner-approval inbox identifies people and agencies by truncated UUID

**What:** `ServiceRequestsPage.tsx:83-84,109-110` renders `#{shortId(r.beneficiary_id)}` and `#{shortId(r.from_mda_id)}`. `ServiceRequest.beneficiary_name` **exists on the type** (`registry/types.ts:106`) and is used correctly 30 lines away in `ActivityDetailPage.tsx:53`.

**Why it matters:** This is the ownership mechanism — the thing PRODUCT.md says a neighbouring product cannot claim. Accepting grants read access to a citizen's full profile and benefit history; declining blocks a sister agency from serving someone. No officer can responsibly do either against `#a3f21b09` from `#7c4e11d2`. In practice this guarantees rubber-stamping or blanket refusal. On the requester's side a decline arrives as a red chip with **no next step** — no "raise a referral instead", no revise-and-resend. The two-sided workflow is a dead end on the side that lost.

**Fix:** Use `beneficiary_name` now. Add `from_mda` name to the API contract. Surface the requesting activity, its catalog programme, and the beneficiary's existing benefit summary in the decision modal — since acceptance grants exactly that. Give a declined requester a next action.

**Suggested command:** `/impeccable clarify web/src/features/registry/ServiceRequestsPage.tsx`

### [P1] Ownership is invisible on the records the user owns

**What:** `BeneficiaryDetailPage.tsx:129` computes `isOwner` solely to gate the Edit button and never displays `owner_mda`. Its Provenance card lists Source / Registered / Record ID / Original ID / Import batch — everything PRODUCT.md Positioning #1 enumerates **except Owner MDA**. Same in `BeneficiaryListPage`, `HouseholdListPage`. `TopBar` never shows the user's acting MDA. A non-owner gets no Owner MDA, no Edit, and no `RequestToServeButton` — three absences to interpret.

**Why it matters:** Principle 1 is "Ownership is visible, always… never discovered by hitting a permission error." The current state is the exact inverse — ownership is legible on *other* MDAs' records in the reveal panel and invisible in the registry the user works in daily. A non-owner hits a dead end with no explanation, which is precisely the turf-conflict experience the product exists to eliminate.

**Fix:** Owner MDA as the **first** Provenance row and a list column. When the viewer isn't the owner, replace the absent Edit button with "Owned by Ministry of Health · you have read access" plus a `RequestToServeButton`. Acting MDA in `TopBar`. (Related: the `.user` chip has `onClick={onOpenUser}` and `AppLayout` never passes `onOpenUser` — a focusable, hover-styled control that does nothing.)

**Suggested command:** `/impeccable clarify web/src/features/registry`

### [P1] The Governor's page is the densest page in the application

**What:** `ExecutiveOverviewTab.tsx` renders 4 KPI panels + 6 delivery figures + 6 coverage figures + up to 6 insights + up to 9 alerts + 4 sparklines + 3 forecast cards + a 6-slice donut + 3 demographic blocks — ~50 figures — beneath a 2-value hero and a 7-control `FilterBar` that persists onto every inner page including the map. ## Questions to Consider

**1. What if the adjudication screen were the only screen — and the import table were merely how you got to it?** The table isn't the work; the ~8% flagged rows are. A full-width one-at-a-time view — incoming left, candidate right, differences highlighted, `S`/`D`/`N` to serve/discard/new, "12 of 150" — would resolve the select-all problem, the find-the-flagged problem, and the flat-peak problem simultaneously.

**2. If the interface never showed the score, would officers make better decisions?** `score 0.87` is a model artefact leaking into human judgement; it invites deference to the number and discourages looking at the fields. Show only the evidence ("Aminu Bello" vs "Aminu Bala", DOB differs by 2 years, same phone) and relegate the score to the audit record. Then thresholds govern *what gets surfaced* and the human governs *what it means* — the actual division of labour the product claims.

**3. What is the interface for the thing this product is actually for — the overlap between MDAs?** Nothing anywhere visualises the central problem statement. There is no gross-vs-net by MDA, no co-service matrix, no "these two agencies are serving the same 340 people". Would the Governor rather see 50 figures, or one picture of where duplication is still happening?

**4. Should "Owner MDA" be a badge rendered by a single shared component?** Ownership is currently a boolean in five permission checks, a column in four places, and nothing at all in the registry's own detail view. One `<OwnerBadge mda isYou />` — dark when yours, outline when not, always carrying the request affordance when not — would enforce Principle 1 by construction. What else here is a *principle* that ought to be a *component*?
